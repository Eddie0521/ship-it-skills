# ship-it：入口

这套流程的核心只有一句话：**main 只放能用的版本；每件事都有一个 issue 说清楚要什么，在分支上做，用 PR 交付，CI 把关，合并时顺手关掉 issue。**

这个技能本身不干活，它负责两件事：判断场景，以及立下所有子技能共用的规矩。


> 范围提醒：这里的 ship 指"把一件事从想法做到合并进 main"。部署上线、发版打 tag、发布到 npm / 应用商店不归这套技能管；用户说的 ship 是这些意思时，不要套用本技能。

## 第一步：判断场景

一个项目的生命周期，以及每一步对应的子技能：

```
new-repo          搭骨架：仓库、测试、CI、PR 模板、分支保护
    ↓
plan-to-issues    和用户讨论方案 → 定稿 → 拆成 issue
    ↓               （别人给来的方案、需求，也从这里进）
issue-to-pr       一个 issue → 一个 PR
    ↓
pr-to-merge       持续跟进 PR：冲突、CI、评审意见，直到能合并
    ↓
合并，issue 自动关闭 → 回到 plan-to-issues / issue-to-pr 做下一个

handoff           旁支：方案定稿后，不是我们自己做，而是交给别人去做
```

看用户现在处在哪一步，转过去：你的环境能直接调用技能（比如有 Skill 工具），就调用对应的子技能；不能的话，直接读它的 SKILL.md。子技能和本技能装在同一个技能目录下，是同级目录，比如 `../plan-to-issues/SKILL.md`。

| 用户的处境 | 转到 |
| --- | --- |
| 还没有仓库，或者仓库是空的、刚建的 | `new-repo` |
| 有一个想法要讨论成方案；或者手上有别人给的方案、需求文档，要变成我们的 issue | `plan-to-issues` |
| 有一个明确的 issue 或小任务，要写代码交付 | `issue-to-pr` |
| 已经有 PR，要处理冲突、修 CI、回评审意见 | `pr-to-merge` |
| 我们的方案或 issue 要交给别人（同事、外包、另一个 AI 会话）去实现，以及验收他们交回来的东西 | `handoff` |

几个容易混的情况：

- **新项目 + 已经有想法**：先 `new-repo`，再 `plan-to-issues`。骨架没好之前别急着写功能，否则第一批代码就没有 CI 把关。
- **别人给我们方案 vs 我们给别人方案**：前者是 `plan-to-issues`（消化成我们的 issue）+ `issue-to-pr`；后者才是 `handoff`。
- **任务很小**（改个错别字、一行配置）：直接 `issue-to-pr`，issue 可以只写一行，甚至跳过，但 PR 和 CI 不跳。
- **判断不了**：问用户一句，并给出你的推断，比如"看起来方案已经定了，要开始拆 issue 吗？"，别猜着往下做。

如果对应的子技能没有装（找不到），就按本文件的规矩和你对该场景的常识去做，并告诉用户缺了哪个子技能。

## 第二步：所有子技能共用的规矩

### 1. 对外操作先给方案，确认再做

建 issue、提交、推送、开 PR、合并、改仓库设置、在 GitHub 上发评论，这些都会留下痕迹，有的还会通知别人。做之前先把**要做什么**摆出来，等用户点头：

- 要建的 issue：标题和正文的草稿。
- 要提交的改动：`git diff --stat`，以及关键文件的 diff。
- 要开的 PR：标题、base ← head、描述草稿。
- 要合并的：CI 状态、评审状态、会关掉哪些 issue。

本地操作（建分支、写文件、跑测试、本地提交前的准备）可以直接做，做完一起汇报。

用户说过"这类操作以后不用问"，就按他说的范围放开，但范围之外的仍然要问。一次确认只管这一次。

为什么：用户要能在任何一步叫停或改方向；而且推到公开仓库的东西，删掉了也可能已经被缓存、被通知出去了。

### 2. 先读仓库自己的规矩

动手前看一眼：`CONTRIBUTING.md`、`.github/pull_request_template.md`、给 agent 的说明文件（`AGENTS.md`、`CLAUDE.md`、`.cursor/rules/` 等）、`README` 里的开发说明、已有的 CI 配置、最近几个提交的信息格式。仓库的规矩优先于本技能的默认做法。

### 3. 绝不做的事

- 跳过、禁用测试，或把测试标成"允许失败"来让 CI 变绿。
- 推空提交，或关掉再重开 PR 来"重新触发"CI。
- 在别人的分支上 rebase、amend、force-push（会弄坏别人的本地副本）。在自己建的分支上，按仓库惯例来。
- 把密钥、`.env`、令牌提交进仓库。
- 没有用户确认就合并。

### 4. 推送前先自证

跑仓库自己的检查（测试、lint、类型检查，看 `package.json` / `Makefile` / CI 配置里写了什么）。然后用挑刺的眼光把自己的 diff 读一遍：CI 会因为什么拒绝它？一次验证过的推送，好过三次碰运气的推送。

### 5. 如实汇报

测试挂了就贴输出；跳过了某步就说跳过了，并说明原因；做完并验证过的就直说"已完成"，别含糊。

## 流程全景（给用户讲解时可以用）

```
规划（大事写设计文档，走一次 PR 定稿）
  ↓
issue（待办：要什么、怎么算做完）
  ↓
分支 → 草稿 PR（越早开越好，CI 每次推送都跑）
  ↓
CI 绿 → 评审 → 合并（PR 里写 Closes #N，合并时自动关 issue）
  ↓
计划变了？回头改 issue / 设计文档，别让文档和代码各说各话
```
