# plan-to-issues：从想法到 issue

目标：**每个 issue 拿到手的人，不用再问"要做什么""做到哪算完"**。

> 共用规矩（详见 `ship-it` 技能）：建 issue、推送文档、开 PR 之前，先把草稿给用户看、等确认。写本地草稿可以直接做。

## 0. 方案从哪来

**和用户讨论出来的**：先讨论，再落笔。
- 先读相关代码，弄清现状，再提方案。别凭印象。
- 一次给一个有倾向的建议，加上关键的取舍。别把五个选项平铺给用户。
- 需要用户拍板的点，集中列出来，每个都带上你的建议。
- 讨论定下来的东西，及时写进文档草稿。聊天记录不是方案。

**别人给来的**（产品需求、客户的文档、上游的 issue、另一个团队的设计）：先消化，再转成我们自己的。
- 读完后列出：缺什么信息、哪里有歧义、和现有代码哪里冲突、哪些做不到。这些要问清楚，问给方案的人，或者让用户去问。
- 转写成我们仓库里的文档或 issue，**注明来源**（链接、日期、版本），方便以后对照原文。
- 不要原样照搬对方的拆分。按我们的代码结构和"每个 PR 能独立合并"的原则重新拆。

方案定了以后，接下来是我们自己做，就继续往下走：拆 issue，然后 `issue-to-pr`。要交给别人做，就拆完 issue 后转 `handoff`。

## 1. 判断规模

| 规模 | 例子 | 做法 |
| --- | --- | --- |
| 小 | 改个文案、修个明确的 bug、加个小开关 | 直接一个 issue，甚至直接 `issue-to-pr` |
| 中 | 一个新功能，涉及几个文件，方向清楚 | 一个 issue，正文里列清单，或者拆成 2–4 个 issue |
| 大 | 牵涉数据结构、接口、多个模块，或者方向还有争议 | **先写设计文档**，走一次 PR 定稿，再拆 issue |

判断不准时，问自己：如果直接开写，最可能在哪一步返工？如果返工点在"方向 / 数据结构 / 接口"，就是大事，先写文档。

## 2. 大事：先写设计文档

放进仓库（比如 `docs/<主题>.md`），不要只放在聊天里：文档和代码放在一起，才不会各说各话。

先读代码再写，结论要能回溯到文件和行号，**别凭印象写现状**。文档结构可以参考：

1. **目标**：做完之后，用户 / 系统能做到什么。尽量写成可测的。
2. **现状**：现在怎么做的、有什么问题（读代码确认过的才写）。
3. **方案**：数据结构、接口、关键流程。写清楚为什么选这个，以及否掉的方案为什么不行。
4. **分期**：每期能独立合并、独立验收、能回滚。
5. **不做什么**：明确划出范围。
6. **开放问题**：需要用户拍板的点，给出你的建议。

开一个文档 PR（标题如 `docs: <主题> 设计`）。开放问题有了答案，就写进文档的"决定记录"，再合并。**定稿合并之后再拆 issue**。

## 3. 拆 issue

**怎么拆**：
- 每个 issue 能**独立做成一个 PR**，合并后 main 仍然能用。
- 一般一个 PR 在 1–3 天的工作量以内。再大就继续拆。
- 先"止血"或打地基，后做功能。被依赖的排前面。
- 一个 issue 一件事。"顺便"做的事另开 issue。

**每个 issue 的正文**（仓库有 issue 模板就按模板来）：

```markdown
## 要什么
（一两句话：目标，以及为什么要做）

## 怎么算做完
- [ ] 可验证的条件 1（比如：某某测试通过；某某接口返回某某）
- [ ] 可验证的条件 2

## 参考
docs/<主题>.md 第 X 节；相关 #N

## 依赖
依赖 #N（没有就写"无"）
```

**给用户看的清单**，一张表即可：

| # | 标题 | 规模 | 依赖 | 验收要点 |
| --- | --- | --- | --- | --- |

用户确认后再建。用你手上有的方式建：`gh issue create`、GitHub 的 API 或 MCP 工具，都没有就把草稿给用户，让他在网页上建。建完把编号回填进依赖关系，并在设计文档的分期表里写上对应的 issue 编号。

## 4. 可选：用 milestone 或 project 串起来

多期的计划，建议一个 milestone 对应一期，或者用 GitHub Projects 看板。这一步不是必须的，问用户要不要。

## 5. 计划会变

做的过程中发现计划不对，就回头改：在 issue 里说明变了什么、为什么；大变动直接改设计文档（走 PR）。不要让 issue、文档和代码三者互相矛盾。
