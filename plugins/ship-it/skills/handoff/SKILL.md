# handoff：交给别人做，再验收回来

关键是**把"做什么、怎么交、什么算完"写在仓库里**，而不是写在聊天记录里。对方随时能查，你验收时也有依据。

> 共用规矩（详见 `ship-it` 技能）：建 issue、开 PR、发评论、合并之前先给用户看、等确认。

## 交出去

### 1. 方案要先入库、定稿

- 方案在 `docs/` 里并且已经合进 main 了吗？没有的话先走 `plan-to-issues` 的文档 PR。
- 检查方案对"另一个人"够不够用：
  - 有没有"给实现者"的部分：先读哪几节、项目约定、绝不能破坏的不变量；
  - 每一期有没有：要改哪些文件、新增哪些测试、怎么回滚；
  - 开放问题是不是都定了。没定的问用户，答案写进文档的决定记录。
- 不够就先补文档（走 PR），再交接。

### 2. 补齐交付用的基础设施

没有的话建议用户加上（各开一个小 PR，参考 `new-repo` 的模板）：
- **CI**：对方推上来就自动跑测试，你不用自己拉代码验证。**先确认 main 上 CI 是绿的**；有本来就挂的测试，先修掉或说明清楚，否则对方分不清是不是自己弄坏的。
- **PR 模板**：等于交付单，对方开 PR 时自动带出"做了什么 / 和方案不一致的地方 / 怎么验证 / 回滚 / 风险"。
- **分支保护**：main 必须走 PR、CI 必须过。

### 3. 选交付形式

先问清楚对方是谁、能接触到什么，再选。不同的形式，交出去的东西不一样：

| 对方 | 交付形式 | 交出去的东西 |
| --- | --- | --- |
| 能进我们仓库的人（同事、协作者） | 同仓库的 issue，指派给对方 | 文档链接 + issue 列表 + 开工消息 |
| 在自己仓库干活的人（外包、开源贡献者） | 对方 fork 后向我们提 PR，或者我们把 issue 抄到对方的跟踪系统 | 同上，外加"PR 提到哪个仓库、哪个分支" |
| 不碰仓库的人（还在评估的外包、产品方） | 打包成一份独立文档（Markdown 或 PDF） | 把方案、issue 清单和验收标准合成一份，不依赖仓库链接也能读懂 |
| 另一个 AI 会话或 agent | 一段开工指令 | 仓库地址 + 文档路径 + 第一个 issue 编号 + 交付格式 + 什么时候必须停下来问人 |

不管哪种形式，**源头都留在我们仓库里**。打包出去的是副本，变更回到仓库里改，再重新导出。

### 4. 按分期建 issue

每期一个 issue（或一个 milestone 加几个 issue），正文：

```markdown
规格：docs/<方案>.md 第 X 节
任务：（复制该期的清单）
验收：
- 测试全过（已知例外：……）
- 本期列出的新测试都有、都过
- 不违反方案里的不变量
依赖：#N
```

### 5. 写开工消息

给用户一段可以直接发给对方的话，讲清四件事：看什么、做什么、怎么交、什么算完。

```
<项目> 的 <功能> 方案在 docs/<方案>.md，先读第 X、Y 节。
从 #<第一个 issue> 开始，一期一个 PR，PR 描述里写 Closes #<issue>。
能开 PR 的时候就先开成草稿，有疑问直接在 PR 或 issue 里问，别攒着。
验收标准是 issue 里的清单，加上文档里的不变量。
<最急 / 最需要注意的一件事>。
方案有写错或做不到的地方，直接在 PR 里改文档并说明理由。
```

### 6. 交给另一个 agent

agent 不会追问"你指的是哪个文档"，所以开工指令要比给人的更具体。原则是**能指向仓库里的东西，就别贴在聊天里**：方案在文档里，任务在 issue 里，进度在 PR 里。换几个 agent 接手都不会丢上下文。

**先看方案在哪**：

- **方案已经合并进 main**（推荐）：agent 从 main 开工。用下面的"开新工作"模板。
- **方案还在一个没合并的 PR 里**：建议先把方案 PR 合并了再派活。agent 基于草稿干活，方案一改，它做的就跟着作废。实在要并行，就让 agent 从方案分支拉自己的分支，PR 的目标分支选方案分支（叫叠加 PR）；方案合并后，再把目标分支改成 main。把这个绕法和风险告诉用户，让用户决定。

**开新工作**的指令模板：

```
仓库：<owner>/<repo>
先读：docs/<方案>.md 的第 X、Y 节（不变量在第 Z 节）
任务：实现 issue #<N>，只做 issue 里列的内容
交付：从最新的 main 开分支，尽早开草稿 PR，描述按仓库的 PR 模板填，写 Closes #<N>
验收：<测试命令> 全过（已知例外：……）；issue 列出的新测试都要有
必须停下来问人的情况：方案和代码对不上；要改方案没提到的文件或接口；要删数据或改数据结构；测试怎么都过不了
不要做：合并 PR；跳过或禁用测试；force-push
```

**接手做到一半的 PR**的指令模板：

```
继续 <owner>/<repo> 的 PR #<N>。
先读 PR 描述、所有评审意见和最新的 CI 结果，再切到这个 PR 的分支（比如 gh pr checkout <N>）。
接着做描述里还没勾上的项，处理未解决的评审意见；在同一个分支上提交，不要新开 PR，不要 force-push。
<同上的验收、停下来问人、不要做>
```

**交付渠道**：看用户手上有什么，从上往下选。没法确认某个渠道在用户那里能不能用，就说明这一点，别替用户假设。

| 渠道 | 怎么做 |
| --- | --- |
| 新开一个 agent 会话 | 在用户用的 agent 工具里新开会话，挂上仓库，粘贴开工指令。最通用 |
| 在 issue / PR 里 @ agent | 仓库装了能响应 @ 提及的 agent 应用或 Action 时，在评论里写 `@<agent> 按 docs/<方案>.md 实现 #<N>` |
| 把 issue 指派给 agent | 用户的平台支持把 issue 直接指派给 agent 时用 |
| 由当前 agent 代派 | 当前环境能创建新会话或子任务时，可以代用户派出去并帮忙盯着 PR。**派之前给用户看开工指令，确认后再派** |

派出去之后，agent 交回来的 PR 照样按下面的"收回来"来验收。

## 收回来：验收 PR

收到对方的 PR 时，按顺序看三样：

1. **测试**：CI 绿不绿？新测试是否覆盖了这一期的清单？没有 CI 的话，本地拉分支跑一遍。
2. **不变量**：逐条对照方案里"绝不能破坏"的那些规则，找对应的代码看。这是对方最容易漏、也最贵的部分。
3. **方案偏差**：PR 描述里"和方案不一致的地方"合不合理？描述里没写、但代码里偏离了方案的，要指出来。合理的偏差，让对方同步改文档；不合理的，在 PR 里说明。

给用户一份验收报告：

```markdown
## 结论：可以合并 / 需要修改 / 需要讨论

## 测试
## 不变量（逐条：✅ / ❌ + 代码位置）
## 方案偏差
## 建议的评审意见（可以直接贴到 PR 上的）
```

评审意见要用户确认后才发到 PR 上：具体到某一行的，用行内评论；方向性的，写在总评论里。都满意了，由用户批准并合并。

## 交接中途

- 对方问的问题，答案如果会影响后续的人，就写回文档或 issue，而不是只在私聊里回答。
- 进度看 issue 列表：开着的、有 PR 关联的、已关闭的。
