# pr-to-merge：把 PR 推到能合并

> 共用规矩（详见 `ship-it` 技能）：推送、在 PR 上回复或解决评审讨论、请求重新评审之前，先给用户看、等确认。本地复现、改代码、跑测试可以直接做。

## 0. 先看全貌

在当前最新的提交上看：能不能合并（有没有冲突）、CI 每一项的状态、所有没解决的评审讨论（包括早先的评审）。**一次处理完所有待办**，别只修最显眼的那一个。

还要分清：**这个 PR 是谁的？**
- 自己开的，或者作者请你帮忙推进的：你负责把它弄到能合并。
- 只是帮忙看看别人的 PR：小而明确的问题可以提议修复；大的改动只提建议，由作者决定。

## 1. 合并冲突（最先处理）

```bash
git fetch origin
git merge origin/main          # 在 PR 分支上
```

- **用 merge，不用 rebase**，尤其是别人的分支：rebase 加 force-push 会把对方本地的副本弄乱。自己的分支按仓库惯例来。
- 锁文件和生成文件（`package-lock.json`、生成的代码）不要手动解冲突，用仓库的工具重新生成。
- 两边都改了同一段逻辑、选哪边都会丢功能的时候，停下来问用户。
- 解决完先跑测试，再推送。

## 2. CI 失败

**先判断是不是这个 PR 的问题**：
- main 上同一项检查也是红的？
- 报错指向的服务或文件，这个 PR 根本没碰过？

是的话，就不是这个 PR 的问题。如果已经有修复（某个 PR、某个 revert），可以把同样的改动带进来，等 main 修好后它自然就没有差异了；没有修复的话，在 PR 上说明哪项检查挂了、为什么不是本 PR 的问题。说明时可以附上建议的补丁，但不要擅自扩大 PR 的范围。

**是这个 PR 的问题，就找根因**：
1. 打开失败的日志，找到第一条真正的错误（不是最后一行）。
2. 在本地**复现**：跑同样的命令。复现不了，就对比 CI 环境（版本、环境变量、操作系统、时区）。
3. 修复，然后证明同一个检查本地能过。

**"偶发失败（flaky）"不是根因**。只有这几种情况可以重跑，而且最多一次：
- 任务死在测试开始之前（拉代码、装依赖、机器丢失）；
- 这个提交之前跑过并且是绿的；
- 为了确认"不是本 PR 的问题"。
第二次还挂，就是真问题。

**绝不**：跳过、禁用测试，或把测试标成允许失败；推空提交来重新触发 CI；关掉再重开 PR。

## 3. 评审意见

| 类型 | 做法 |
| --- | --- |
| 小而明确（命名、补个测试、一个函数内的重构、明显的 bug） | 改，推送，在讨论里用一句话说明改了什么，然后标为已解决 |
| 大（跨多个文件的重构、接口或数据结构变更、方向性意见） | 在别人的 PR 上：回复你的方案，由作者决定；在自己的 PR 上：把方案和取舍告诉用户，确认后再做 |
| 标了 nit / optional / suggestion 的 | 不单独为它推送。能顺手带进下一次推送就带上，否则回复一句"先保留，原因是……" |
| 机器人提的 | 当成待核实的说法：找到一条从真实输入到故障的路径，路径成立且修复的代价合理就修；否则回复你找的路径和不修的理由，交给用户决定 |
| 问"为什么这么做"的 | 根据代码和设计回答；回答不了的就问用户 |

分不清大小的，按大的处理。

推完修复后：标记已解决的讨论；对方之前选了"要求修改"的，请他重新评审。

## 4. 推送前自证

跑仓库自己的检查；修 CI 时要先复现失败、再证明修好；用挑刺的眼光读一遍这次的 diff。**每次修复只做失败或评审要求的那些，不顺手扩大范围**。

## 5. 什么时候算完

CI 全绿 + 没有冲突 + 没有待处理的评审讨论（+ 仓库要求的批准）。这时告诉用户"可以合并了，等你确认"。
如果只差别人的批准：说一次"在等评审"，然后别为了它去推提交。推送没法替人点批准，反而可能让已有的批准失效。
